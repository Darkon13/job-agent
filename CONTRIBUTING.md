# Как участвовать в разработке

Спасибо за интерес к Job Agent. Проект развивается как локальный
платформо-независимый сервис автоматизации поиска работы: core не знает о
конкретных платформах, а каждая платформа подключается отдельным адаптером.

## Что можно предложить

- новый адаптер платформы или новый транспорт для существующего;
- исправление ошибки с воспроизводимым примером;
- улучшение dashboard, API, документации или тестов;
- новый processor/operator (детерминированный, шаблонный, LLM) без platform
  side effects.

## Подготовка

```bash
git clone https://github.com/<owner>/job-agent.git
cd job-agent
go build ./...
make verify     # go test -race ./..., go vet, git diff --check
make smoke      # runtime smoke на пустой БД
```

Для browser-worker:

```bash
cd browser-worker
npm ci
npm run typecheck
npm test
```

Требования: Go из `go.mod`, Node 22 для worker. Docker не обязателен для
разработки.

## Правила

1. Одна PR-тема — один сфокусированный набор коммитов. Не смешивайте
   рефакторинг и новое поведение.
2. Соблюдайте границы слоёв: platform-specific код — только в
   `adapters/<platform>`; `core` и `workflow` не импортируют адаптеры.
3. Ошибки возвращаются как `*core.OperationError` с нормализованной категорией.
   Сообщения не должны содержать токены, cookies, тексты резюме и другие
   персональные данные.
4. Новое поведение сопровождается тестами (`make verify`) и записью в
   `docs/changelog.md`. Пользовательские интерфейсы и контракты платформ
   документируются в `docs/`.
5. Секреты, storage state, `data/` и персональные манифесты не коммитятся.
6. Если фича не проверена живьём на реальной платформе — явно напишите это в
   описании PR и в документации.

## Новый адаптер

Пошаговое руководство, список capability-интерфейсов и чек-лист находятся в
[`docs/writing-adapters.md`](docs/writing-adapters.md). Для нового адаптера
приложите:

- фабрику и регистрацию в composition root;
- валидацию adapter-specific config;
- contract-тесты и документацию живых запросов;
- описание ограничений (какие операции не поддержаны и почему).

## Автоматизация в репозитории

- CI на каждый push и PR: `make verify`, `make smoke`, browser-worker
  (`typecheck` + tests).
- Docs workflow собирает вики на PR и публикует её из `main`.
- PR-бот ставит лейблы по затронутым путям и ведёт один комментарий со статусом
  проверок.
- Dependabot раз в неделю обновляет Go, npm и GitHub Actions.
- `main` защищён: нужен зелёный CI, аппрув ревьюера и линейная история;
  force-push и удаление ветки запрещены.

## Pull request

Заполните шаблон PR: что изменено, как проверялось, что осталось
непроверенным. Перед отправкой убедитесь, что `make verify` зелёный и worktree
не содержит посторонних изменений.
