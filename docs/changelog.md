# Изменения

## 1.9.0

- Отклик, остановленный проверкой HH (`hhcaptcha`), можно провести вручную
  через реальный браузер профиля. В dashboard у такого отклика появляется
  кнопка «Проверка», а в CLI — `job-agent captcha solve <application_id>`:
  сервис открывает вакансию, нажимает «Откликнуться», при необходимости
  показывает картинку капчи в dashboard или терминале и принимает ответ.
- Если браузерная сессия не получает капчу (HH проверяет только прямой API),
  отклик отправляется сразу, сопроводительное письмо прикладывается после
  отклика, а подтверждением занимается обычный retry-пайплайн.
- `job-agent captcha list` показывает отклики, ожидающие капчу.

## 1.8.5

- Отклик, остановленный проверкой платформы, получает понятную причину:
  `captcha_required` («HH просит пройти капчу») для капчи и
  `platform_validation_required` для остальных случаев. Раньше сохранялся
  `qualified`, и dashboard показывал странную пару «Не отправлено / Проверки
  пройдены».

## 1.8.4

- Кампания живёт не дольше трёх часов: если отклик застрял (блок платформы,
  капча, ожидание pacing), run завершается сам и перестаёт держать removal
  guard — из-за 5 зависших кампаний удаления падали с «belongs to a running
  campaign».
- Ожидание pacing-слота до двух минут теперь пережидается внутри обработчика,
  а не повторной попыткой: 7 submit-задач сгорали с «waiting for its pacing
  slot».
- Ответ HH с `hhcaptcha` распознаётся как требование подтверждения с понятным
  сообщением вместо серии temporary-повторов.

## 1.8.3

- Job `profile.activity.maintain` пишет в лог результат каждого запуска:
  профиль, текущий score, сколько вакансий просмотрено и сколько кандидатов
  нашлось; при score 100 пишется причина пропуска.

## 1.8.2

- HH 403 на отклик (временная блокировка аккаунта или дневные лимиты) больше не
  сжигает отклик permanent-ошибкой: и preflight, и сам submit переходят в
  retryable-категорию, а тело ответа (до 200 символов) попадает в сообщение
  задачи для диагностики.

## 1.8.1

- Синк чата больше не падает, когда платформенный timestamp сообщения опережает
  локальные часы: время наблюдения презентации ограничивается состоянием
  диалога, метаданные сохраняются.
- `test.capture` для вакансии без анкеты завершается пропуском, а не
  permanent failure: если платформа убрала опросник, задача ничего не ломает и
  отклик можно повторить из UI.

## 1.8.0

- Анкеты: флаг «в банк» теперь у каждого вопроса, а не только у всего пакета.
- Новая job `application.answer_covered`: отклики, чья анкета полностью
  покрыта reviewed-банком, отправляются автоматически; частично покрытые
  остаются в ревью.
- Retention: `validation_stale_after` задаёт отдельное окно для анкет, которые
  так и не стали откликами.
- Утилиты (`check`, `trigger`, `approve`, `browser-state`,
  `question-bank-import`) стали подкомандами `job-agent`; старые бинарники
  остались тонкими обёртками.
- Релизные архивы содержат `compose.yaml`, `.env.example` и примеры `deploy/`;
  образы публикуются в GHCR (`job-agent` и `job-agent-browser-worker`).

## 1.7.2

- Отзыв отклика на HH действительно скрывает тему: форма отправляет поле
  `topic`, а ответ без подтверждения (`<doc/>`) больше не считается успехом —
  иначе локальная запись удалялась, а отказ оставался на платформе.
- Активность: job `profile.activity.maintain` снова находит свежие вакансии —
  поиск резолвится у фасада адаптера, а не у browser-ридера, из-за чего запуск
  падал с `unsupported`.
- Чаты с неотвеченной анкетой синхронизируются по расписанию, даже если выпали
  из окна недавней активности: reviewed-ответ уходит без открытия чата.
- «Проверки и опросники»: поиск по вопросу и определению, пагинация и локальное
  скрытие сессии (`cancel`) без действий на платформе.

## 1.7.1

- Удаления откликов, заблокированные running-кампанией или незавершённой
  tailoring saga, повторяются после завершения владельца, а не падают
  permanently.
- Live-наблюдение при удалении валидируется по свежему времени: повторное
  чтение платформенного состояния больше не выглядит «устаревшим», и удаление
  доходит до конца.
- Write-транзакции SQLite берут блокировку сразу (`_txlock=immediate`) —
  исключены падения `SQLITE_BUSY` при read→write апгрейде, из-за которых
  `conversation.discover` исчерпывал попытки.
- Повторяющийся вопрос в одной попытке теста больше не отклоняет attempt:
  манифест попытки — множество наблюдённых вопросов.

## 1.7.0

- Hot-load, финальная фаза: изменения кампаний и поисков применяются без
  рестарта — маршруты атомарно пересобираются в работающем campaign handler
  (`ReplaceRoutes`), definitions кампаний перечитываются тем же watcher'ом.
  Рестарт остаётся только для `database.path`, `server.*`, adapters и
  `state_file`.

- Dashboard показывает состояние конфига: digest, время последнего применения,
  число определений и текст последней ошибки (если перезагрузка отклонена) —
  в шапке рядом с версией и в `dashboard/summary.config_status`.

- GC чистит очередь «Нужно участие»: retention получает
  `remove_waiting_validation: true` и удаляет анкеты/тесты, которые так и не
  стали откликами и лежат старше `stale_after` (сначала самые старые).
  Платформенная часть не нужна — у таких записей нет negotiation; tombstone
  сохраняет dedup. Пример конфига обновлён.

- Hot-load, фаза 2: изменения конфига подхватываются сами — watcher раз в
  5 секунд сверяет digest собранного конфига (включая include-файлы) и
  применяет расписания без рестарта; `SIGHUP` остаётся ручным триггером.
  Изменения кампаний и поисков по-прежнему требуют рестарта.

- Уборка отказов стала чаще: `cleanup-rejected-applications` теперь каждые
  3 часа вместо раза в сутки — отзыв и скрытие откликов на HH догоняют
  платформенные отказы в тот же день.

- Job активности открывает только не просмотренные ранее вакансии из
  глобального поиска: свежие карточки, отфильтрованные по локальной истории
  `vacancy.inspected`; очередь откликов больше не используется, а запуск без
  global-поиска просто пропускается.
- Hot-load конфига, фаза 1: `SIGHUP` перечитывает и валидирует файл, затем
  синхронизирует расписания и job-дефиниции без рестарта; при ошибке старый
  конфиг продолжает работать. Изменения кампаний и поисков пока требуют
  рестарта (регистрируются в campaign handler).

- Job активности берёт вакансии из глобального поиска профиля (а не только из
  очереди откликов) и пропускает запуск, если процент уже 100: просматривать
  можно любые свежие вакансии, а на максимуме задача зря не тратит запросы.

- Job `profile.activity.maintain`: открывает реальных вакансий-кандидатов из
  очереди профиля браузерной сессией (с паузой между просмотрами), пишет
  `vacancy.inspected` и ничего не отправляет. Процент активности читается
  прежним `observe-activity`, теперь его можно поддерживать.

- Зафиксирован план горячей перезагрузки конфига
  (`docs/next-config-reload.md`): SIGHUP и watcher, горячая часть
  (расписания, поиски, пулы, модели, политики) применяется без рестарта,
  железная часть (database, listen, adapters, state_file) — только рестартом.

- Runbook: описано ручное снятие протухшего runtime-lease
  (`delete from runtime_instances`) после серии быстрых пересозданий
  контейнера, когда guard не освободился сам за 90 секунд.

## 1.6.0

- Отклики с решением `unsupported_response_flow` больше не попадают в «Не
  отправлено»: показываются в «Нужно участие» с понятной причиной «Платформа
  вернула неподдерживаемый сценарий отклика» (например, рекламный flow в
  popup HH).

- Ответ на опросник отправляется синхронно (`?live=1`), поэтому бейдж
  «опросник» снимается сразу после ответа: диалог переходит в обычный, а если
  платформа закрыла его после опроса — убирается из списка. Когда работодатель
  напишет снова и чат откроется, он снова покажется как обычный диалог.

- SSE стал секционным: `event: dashboard` присылает только изменившиеся разделы
  (`conversations`, `tasks`, `applications`), dashboard обновляет только их и
  не трогает открытый чат из-за счётчиков задач; при скрытой вкладке события
  игнорируются, а при возврате страница обновляется.

- Если чат закрыт работодателем, dashboard честно говорит «Работодатель закрыл
  чат» и убирает диалог, вместо ложного «Сообщение отправлено» и зависшего
  пузыря; синхронная отправка возвращает признак `closed`.

- Закрытие чата ловится как конец опросника: когда синк каталога видит, что
  диалог закрыт/отклонён/архивирован, запланированные напоминания этого чата
  отменяются сразу, а не висят до срабатывания.

- Ответ на опросник в чате отправляется сразу, без диалога подтверждения:
  один клик по варианту ставит отправку в работу.

- Сообщения из dashboard отправляются сразу: `POST …/messages?live=1` вызывает
  тот же обработчик, что и очередь, синхронно и с тем же idempotency-ключом;
  при ошибке запрос откатывается в durable-очередь, поэтому дубликат на HH
  невозможен. Dashboard показывает «Сообщение отправлено» без ожидания тика.

## 1.5.0

- Чат подтверждает отправку за секунды: после постановки задачи dashboard сам
  подтягивает историю до появления сохранённого сообщения (до 15 секунд,
  без ожидания тика).
- Поток событий `GET /api/v1/events` расширен до `event: dashboard`: в отпечаток
  входят и счётчики задач, поэтому список чатов, задачи, отклики и проверки
  обновляются по событию, а 30-секундный опрос остаётся страховкой.

- Открытый чат читается вживую: `GET /api/v1/conversations/{id}/messages?live=1`
  синхронно обновляет историю через транспорт профиля (таймаут 10 секунд,
  ошибка не ломает ответ), а фоновая цепочка задач остаётся надёжным путём.

- Отправка в чате теперь оптимистичная: сообщение сразу появляется в переписке
  со статусом «Отправляется…», ввод очищается мгновенно, а подтверждённое
  сообщение из очереди заменяет временный пузырь при следующем обновлении
  (SSE или тик).

- Follow-up умеет выбирать не один чат, а несколько: `limit` задаёт число
  напоминаний за запуск, `all: true` берёт все подходящие (до 50).
  В примере конфига job напоминает во всех чатах, молчащих 5 дней
  (`minimum_silence: 120h`).
- SSE-поток чатов теперь реально стримится через dashboard: регистратор
  access-log пропускает Flush, а обратный прокси флашит сразу.

- Чаты обновляются по событию: `GET /api/v1/events` (SSE) присылает
  `event: conversations` при изменении ревизии диалогов, dashboard сразу
  перечитывает список и открытый чат; тридцатисекундный опрос остался только
  страховкой. Исходящий keep-alive и авто-переподключение EventSource.

- Чаты в dashboard открываются быстрее: при выборе диалога сразу ставится
  приоритетный `conversation.sync`, а история перечитывается через несколько
  секунд, не дожидаясь десятиминутного тика. План перехода на SSE и
  оптимистичную отправку — в `docs/next-conversation-transport.md`.

- Закрытые чаты убираются сразу: если платформа отказала в записи
  («HH conversation is not writable»), диалог переводится в `closed`, снимается
  с dashboard (по умолчанию показываются только активные) и не висит ошибкой в
  задачах. Следующий синк каталога снова покажет чат, если он открылся.

- У job появилось необязательное поле `description`: свой текст показывается в
  dashboard вместо технического типа действия (пример конфига обновлён).
- Закрытая или удалённая вакансия при чтении карточки больше не роняет отклик
  в `permanent_failure`: HH-страница распознаётся, отклик получает решение
  `vacancy_closed` и освобождает бюджет.

- Follow-up: стратегия `longest_silence` выбирает диалоги по длительности тишины
  в любую сторону — ответ «ожидайте» и последующее молчание тоже считается.
  Якорь, cooldown и `minimum_silence` отсчитываются от времени последнего
  сообщения; пример конфига переведён на эту стратегию.

## 1.4.0

- Tailoring умеет переписывать опыт: `tailoring.experience` задаёт
  `write`/`readonly` **объектами** резюме (`title`, `keySkills`, `about`,
  `experience.<id>`, `experience.#N`, `experience.<id>.description`,
  `experience.order`), поддерживает несколько групп с разными инструкциями для
  разных наборов блоков и перестановку блоков. Позиции, компании и даты не
  меняются; числа, e-mail и ссылки проверяются на заземлённость, ошибка группы
  пропускается, при полном провале резюме остаётся текущим. По умолчанию
  выключено и на сервере пока не подключено.

- Review-сессии в dashboard показывают тип ответа и число оставшихся вопросов,
  а галочка «Сохранить в банк» решает, попадёт ли ответ в переиспользуемый блок
  (по умолчанию да). API принимает флаг `bank`; при `bank: false` ответ остаётся
  локальным для сессии и не расширяет банк. Для чатов банк пока не используется.

- Активность профиля снова видна в метриках: наблюдатель читает виджет
  «Ваша активность» с корневого `hh.ru` (авторитетный процент и флаг
  показа), а dashboard показывает карточку «Активность», когда платформа её
  отдаёт.
- В пример конфига добавлена ежедневная job `follow-up-unanswered`: одно
  напоминание о себе в самом старом неотвеченном чате (тишина 72 часа,
  максимум одно, отмена при входящем сообщении).

- Удаление откликов и GC теперь убирают отклик и на HH: ожидающий отклик
  отменяется (`decline`), закрытый/скрытый уходит в архив (`trash`) вместе с
  чатом переговоров. Локальная запись снимается только после успеха
  платформенного действия; для профилей без наблюдателя сохраняется локальная
  семантика.
- Ежедневная job `cleanup-rejected-applications` чистит отказы и устаревшие
  ожидающие отклики (`application.retention`, профили массивом); retention
  переиспользует свежее состояние (окно 10 минут) вместо повторного чтения
  всего списка откликов на каждое удаление.

- Fallback-цепочки поисков стали явными: `searches[].fallback` раскрывается
  транзитивно при загрузке конфига, порядок цепочки сохраняется, циклы и
  неизвестные ссылки отклоняются. Job с `routes` получает раскрытую цепочку в
  payload, поэтому dashboard показывает фактический маршрут.

- Dashboard: «Открыть анкету» у откликов из «Нужно участие» запускает
  захват анкеты (`test.capture`) и переводит к разделу «Проверки и опросники»,
  где анкета заполняется прямо в dashboard; ответы уходят на HH, и пайплайн
  отклика разблокируется. Новый endpoint
  `POST /api/v1/applications/{id}/questionnaire` только ставит захват в
  очередь и ничего не отправляет.

## 1.3.0

- Фильтры квалификации получили `include_all` и `exclude_all` рядом с
  `include_any`/`exclude_any`: можно требовать все термины сразу (AND) и
  исключать вакансию только при полном наборе исключающих терминов.

## 1.2.1

- Dashboard: объединённый job с массивом профилей показывает расписание одной
  строкой, а не повтором на каждый профиль.
- Dashboard: профили объединённого job показываются каждый на своей строке.

## 1.2.0

- Dashboard: отклики со статусом `skipped` и причиной «нужно заполнить анкету
  или пройти тест» показываются в группе «Нужно участие» с кнопкой
  «Повторить», а не теряются в «Не отправлено». Рассылка такие отклики не
  переотправляет: dedup и `validation_action: skip` оставляют их до ручного
  повтора.

- Профильные jobs можно объединять: `action.profiles` принимает массив
  профилей с общим расписанием, одно срабатывание создаётся на каждый профиль.
  Одинаковые задачи (`resume.touch`, `profile.session_refresh`,
  `conversation.sync`, `profile.activity.observe`, `application.state.sync`)
  больше не дублируются: пример конфига и quickstart сжаты с 12 jobs до 7.
  Активная cron-задача проверяется per tag+profile, поэтому профили одного job
  не блокируют друг друга.

- Появился read-only job `application.state.sync`: состояния откликов читаются
  через браузерную сессию профиля (страница откликов HH), обновляют карточки
  dashboard и больше не остаются «не синхронизированными». Планировщик умеет
  пропускать срабатывание без создания задачи, если у всех целей рассылки
  исчерпан дневной лимит откликов; расписание при этом сдвигается на
  следующий cron. Рассылки в примере конфига теперь запускаются каждый час.

- Поиски: глобальный запрос сузился до `(Go OR Golang OR Golang-разработчик)
  AND (NOT Frontend NOT Fullstack NOT Rust)`, а `similar_resume`-маршруты
  больше не задают `text` — они берут любые вакансии из подходящих к резюме,
  а отбор по квалификации остаётся за фильтрами профиля.

- Dashboard: таблица «Автоматизация из конфигурации» показывает параметры
  действия (профили, маршруты, цель, max_in_flight, резюме), cron-расписание с
  таймзоной и jitter, а также обратный отсчёт до следующей постановки задачи в

  сборки и переноса образов.

  могут уложить навыки в лимит (или модель вернула невалидный план), отклик

  релевантную сортировку HH; для подбора по резюме сортировку лучше не задавать.

  `similar_vacancy` принимают современные work-поля и при их наличии идут

  результатам любого source, включая `related_vacancy`.

- Job `profile.session_refresh`: по расписанию перечитывает cookies из live
  browser-контекста, оставляет только HH-домены и атомарно обновляет
  `state_file` (`0600`), чтобы backend не работал по протухшему снимку сессии.

- Имя и контакты для писем резолвятся при старте из live-профиля
  (`firstName`, `lastName`, `web/email`, `communicationMethods`); блок
  `profiles[].contacts` остался fallback-ом для полей, которых нет на
  платформе.

- `profiles[].contacts` (`first_name`, `last_name`, `email`, `telegram`):
  в шаблонах писем доступны как `{{.Profile.*}}`, для модели обезличиваются в
  `{email}`/`{telegram}`/`{first_name}`/`{last_name}` и подставляются после
  валидации. Письмо и «О себе» начинаются с контактов, чтобы рекрутер мог
  связаться напрямую.

- Tailoring переживает лимиты провайдера: temporary/rate-limit/timeout ответы
  повторяются один раз, при повторной неудаче навыки остаются текущими, а не
  откатываются в детерминированную политику (та могла упереться в лимит 30 и
  уронить отклик); «О себе» тоже делает одну повторную попытку.

- `models[].reasoning_effort` (`none`/`low`/`medium`/`high`) для
  reasoning-моделей; chat completions получает явную схему JSON-ответа, потому
  что JSON mode не проверяет форму. Без схемы DeepSeek возвращал свои имена
  полей, а `deepseek-flash` тратил весь `max_tokens` на reasoning.

- Tailoring навыков умеет удалять теги только под добавления: `allow_removals`
  разрешает модели решение `remove` с evidence, validator применяет ровно
  столько удалений, сколько нужно для лимита после добавлений, игнорирует
  лишние и запрещает удаление несуществующих и всех навыков.

- Второй тип model provider — `openai_chat` (OpenAI-совместимый chat
  completions, по умолчанию DeepSeek): structured output через JSON mode и
  строгий локальный decoder, работает для писем, ответов и tailoring.
- Исправлено: OpenAI Responses client не реализовывал `Select` из контракта
  tailoring skills, из-за чего skills-модель не подключалась.

- Справочник: [«Письма и пулы»](reference/messages.md) — пример `message.json`,
  формат пула, стратегии `first`/`stable_hash`, контекст Go-шаблонов и
  ограничения `Attributes`.

- Временная подстройка резюме умеет переписывать «О себе» под вакансию:
  `applications.tailoring.about` получает наблюдаемый контекст резюме (заголовок,
  навыки, опыт, образование, языки), `resume_facts_file` не обязателен;
  локальная валидация покрывает контекст резюме и вакансии, а при сбое модели
  текущий текст сохраняется. `skills` и `about` объединяются в chain и могут
  включаться независимо.
- Модель для сопроводительных получает обезличенный контекст: личные значения
  из `facts.placeholders` и работодатель заменяются плейсхолдерами
  (`{name}`, `{company_name}` и т.д.), валидатор принимает только объявленные
  плейсхолдеры, а реальные значения подставляются локально после проверки
  evidence и до сохранения письма. Необъявленный плейсхолдер уходит в
  fallback-письмо.
