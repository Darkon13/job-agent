# Быстрый транспорт для чатов в dashboard

## Проблема

Чтение и отправка сообщений идут через durable-очередь (`conversation.sync`,
`conversation.send`), каталог обновляется по расписанию раз в 10 минут, а
dashboard опрашивает summary раз в 30 секунд. Для интерактивной переписки это
слишком медленно: открытый диалог выглядит «замороженным», новое сообщение
появляется только после тика, отправка не даёт мгновенного отклика.

## Целевая схема

1. **SSE-поток** `GET /api/v1/conversations/events`: backend пушит события
   диалогов и сообщений (новое сообщение, смена статуса, результат отправки,
   обновление каталога). Dashboard подписывается на поток и держит выбранный чат
   в памяти; SSE выбран вместо WebSocket как более простой путь — он уже
   используется для входа в HH, сам переподключается и проходит через
   dashboard-proxy.
2. **Интерактивное чтение**: при открытии чата dashboard просит историю;
   backend отдаёт её из БД, а параллельно поднимает `conversation.sync` с
   высоким приоритетом и публикует результат в SSE. Периодический discover
   остаётся только для фонового отслеживания.
3. **Оптимистичная отправка**: сообщение сразу рисуется как «отправляется»,
   фактическая отправка остаётся durable-задачей; её результат приходит по SSE
   и заменяет оптимистичный пузырь на подтверждённый или ошибку. Idempotency,
   retry и лимиты не меняются.
4. **Прямой RPC к browser-worker** (вторая фаза): быстрый путь чтения истории и
   отправки в обход очереди для интерактивных запросов; durable-остаётся для
   фоновых операций.

## Фазы

1. Синк по открытию чата (сделано): `POST /conversations/{id}/sync` при выборе
   диалога + повторное чтение истории через несколько секунд.
2. SSE-поток событий чатов (сделано): `GET /api/v1/events` шлёт
   `event: conversations` при смене ревизии диалогов; dashboard обновляет
   список и открытый чат по событию, тридцатисекундный опрос остался страховкой.
3. Оптимистичная отправка и подтверждение через SSE.
4. RPC-путь к browser-worker для интерактивных чтений.

## Ограничения

- Секреты и содержимое переписки не попадают в логи и метрики.
- События SSE не заменяют БД: источник истины остаётся прежним.
- Browser-сессия по-прежнему сериализует запись по профилю.
