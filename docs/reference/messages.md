# Сопроводительные письма: шаблоны и пулы

Письмо для отклика берётся ровно из одного источника в `applications` профиля.
Это может быть статический текст, inline-шаблон или именованный файл пула.
Модель не является отдельным источником: она лишь переписывает один из
настроенных вариантов и обязательно требует его как fallback.

| Поле | Формат | Когда использовать |
|---|---|---|
| `message` | готовый текст без подстановок | одно письмо для всех вакансий |
| `message_template` | Go-шаблон прямо в конфиге | короткий шаблон без отдельного файла |
| `message_template_file` | путь к JSON-файлу пула | несколько вариантов, повторное использование, ревью в Git |

Одновременно разрешён только один источник. Если задан `applications.model`,
источник обязателен и используется, когда модель вернула ошибку или не прошла
локальную валидацию.

## Пример файла пула

`deploy/messages/backend.json` в репозитории — готовый стартовый пример:

```json
{
  "strategy": "stable_hash",
  "templates": [
    {
      "tag": "concise",
      "template": "Здравствуйте! Меня заинтересовала вакансия {{.Vacancy.Title}} в {{.Vacancy.Employer}}. Мой основной фокус — backend-разработка: Go, Python, REST API, PostgreSQL, Docker и автоматизированное тестирование. Буду рад обсудить задачи команды и подробнее рассказать о проектах."
    },
    {
      "tag": "project-focus",
      "template": "Здравствуйте! Откликаюсь на {{.Vacancy.Title}} в {{.Vacancy.Employer}}. Разрабатываю backend-сервисы на Go и Python, работаю с PostgreSQL, Docker, REST API и автоматизированными тестами. Готов подробнее обсудить релевантные проекты и задачи команды."
    }
  ]
}
```

Подключение в профиле:

```jsonc
"applications": {
  "mode": "submit",
  "message_template_file": "messages/backend.json"
}
```

Путь резолвится относительно файла, который объявил поле, — пул можно
переносить между каталогами вместе с include-фрагментом.

## Формат пула

| Ключ | Обязателен | Смысл |
|---|---|---|
| `strategy` | нет | `first` (по умолчанию) или `stable_hash` |
| `templates[]` | да | варианты письма: `tag` и `template`, теги уникальны |
| `template` | нет | устаревшая форма одного письма; нормализуется в пул из одного варианта с тегом `default` |

`templates` и `template` нельзя смешивать в одном файле. Tag самого пула не
задаётся в файле: им становится имя файла без расширения. Вместе с тегом
выбранного варианта он сохраняется в provenance отклика, поэтому после смены
содержимого видно, какая ревизия пула использовалась.

### Стратегии выбора

- `first` — всегда первый вариант. Подходит, когда пул постепенно наполняется,
  а новое письмо должно вытеснить старое.
- `stable_hash` — вариант выбирается детерминированно по паре
  «профиль + платформа + external vacancy ID». Один и тот же отклик при retry
  получает тот же вариант, а разные вакансии равномерно распределяются по
  пулу. Это удобно для A/B формулировок без случайности при повторной отправке.

### Правила загрузки

- пул требует хотя бы один непустой вариант;
- пустые или повторяющиеся `tag` отклоняются;
- шаблон компилируется и один раз исполняется на этапе загрузки конфига;
- итоговый текст проверяется на UTF-8 и лимит 10 000 символов, поэтому
  сломанный шаблон не дойдёт до первой живой отправки.

## Синтаксис шаблона

Шаблоны — это стандартный Go `text/template`, а не подстановка
`{{namespace.value}}`:

```json
{
  "tag": "with-skills",
  "template": "Здравствуйте! Откликаюсь на {{.Vacancy.Title}}.{{if .Vacancy.KeySkills}} Особенно близки темы: {{range $index, $skill := .Vacancy.KeySkills}}{{if $index}}, {{end}}{{$skill}}{{end}}.{{end}}"
}
```

Доступны встроенные возможности пакета: `if`, `with`, `range`, `printf`,
`len`, `index` и другие. Своих функций нет, поэтому логику лучше держать в
вариантах пула, а не в сложном шаблоне.

`missingkey=error` включён: обращение к несуществующему ключу факта —
ошибка загрузки конфига, а не пустая строка в письме. Опечатка в имени
факта будет найдена сразу.

## Доступный контекст

| Выражение | Значение |
|---|---|
| `{{.Vacancy.Title}}` | название вакансии |
| `{{.Vacancy.Employer}}` | работодатель (может быть пустым) |
| `{{.Vacancy.URL}}` | ссылка на вакансию |
| `{{.Vacancy.Description}}` | описание вакансии |
| `{{.Vacancy.KeySkills}}` | массив ключевых навыков |
| `{{.Vacancy.Platform}}` | платформа, например `hh` |
| `{{.Vacancy.ExternalID}}` | внешний ID вакансии |
| `{{.Vacancy.State}}` | состояние вакансии |
| `{{.Vacancy.PublishedAt}}` | время публикации |
| `{{.Profile.FirstName}}`, `{{.Profile.LastName}}` | имя и фамилия из `profiles[].contacts` |
| `{{.Profile.Email}}`, `{{.Profile.Telegram}}` | контакты из `profiles[].contacts` |
| `{{.Resume.ResumeID}}`, `{{.Resume.FactsTag}}` | идентификаторы резюме и набора фактов |
| `{{.Resume.Facts.some_key}}` | явный факт из `resume_facts_file` |
| `{{.ApplicationID}}`, `{{.ProfileID}}` | ID отклика и профиля |

Для совместимости со старыми шаблонами доступны плоские `{{.Title}}`,
`{{.Employer}}`, `{{.URL}}`, `{{.Description}}` и `{{.KeySkills}}`. Новые
шаблоны лучше писать через `.Vacancy`: тот же контекст используется моделью.

Имя, фамилия и контакты объявляются один раз в `profiles[].contacts` и не
требуют файла фактов. Типовое начало письма:

```json
"template": "{{if .Profile.Telegram}}Telegram: {{.Profile.Telegram}}\n{{end}}{{if .Profile.Email}}Email: {{.Profile.Email}}\n\n{{end}}Здравствуйте! ..."
```

Если контакты не заданы, условия отрендерят письмо без пустых строк.

`{{.Resume.Facts.*}}` работает только при заданном `resume_facts_file`.
Ключ `placeholders` в фактах зарезервирован под обезличивание контекста модели:
в шаблонах его использовать не нужно.

Ограничение текущей версии: `{{.Vacancy.Attributes.*}}` доступен только для
ключей, существующих в момент проверки шаблона. При загрузке конфига словарь
пуст, поэтому такие обращения отклоняются — используйте стабильные поля выше.

## Модель и плейсхолдеры

Если включён `applications.model`, fallback-письмо всё равно должно быть
настроено. Перед вызовом модели личные значения из `facts.placeholders` и
название работодателя заменяются на `{name}`, `{company_name}` и т.д., после
локальной валидации подставляются обратно. Это другой механизм, чем
`text/template`:

- `{{.Vacancy.Title}}` — подстановка в шаблоне письма;
- `{company_name}` — маска для обезличенного контекста модели.

Подробнее: [Модель для сопроводительных](recipes.md#модель-для-сопроводительных)
и [Cover letter routing](../next-cover-letter-routing.md).

## Переопределение правилами работодателя

`applications.employer_rules[]` может выбрать отдельный пул или модель для
совпавшей компании. Тогда основное `message_template_file` остаётся письмом по
умолчанию, а правило применяет свой пул. У skip/review-правил письмо не
используется вовсе.

## Проверка

Отдельной команды `validate` пока нет: конфиг проверяется при старте сервиса,
поэтому ошибки загрузки видны в логе сразу. Для работающего сервиса состояние
показывает `job-agent-check` (см. [Quickstart](../quickstart.md)). Tag пула,
tag варианта и digest содержимого сохраняются в provenance отклика; в текущем
dashboard они не отображаются.
