# `profiles[].applications.tailoring`

Временная подстройка резюме перед откликом: сервис снимает snapshot,
применяет план процессоров, отправляет отклик и восстанавливает исходное
состояние. Полный протокол — в
[Временный tailoring резюме](../../application-resume-tailoring.md).

## Пример

```json
"tailoring": {
  "skills": {
    "enabled": true,
    "maximum": 30,
    "allow_removals": true,
    "model": {"provider": "deepseek", "prompt_version": "v1", "instruction": "Добавь релевантные навыки вакансии", "timeout": "60s"}
  },
  "about": {
    "enabled": true,
    "maximum_runes": 600,
    "model": {"provider": "deepseek", "prompt_version": "v1", "instruction": "Подгони «О себе» под вакансию", "timeout": "60s"}
  }
}
```

Tailoring работает только в `mode: submit` и требует резюме. Без блока
`tailoring` отклик готовится как раньше.

!!! warning "Ещё не реализовано"
    Подстройка описаний опыта (`tailoring.experience`: важное вверх, вплетение
    реально использованных технологий вакансии) спроектирована, но пока
    доступны только `skills` и `about`.

!!! note "Тестируется"
    `about` и `skills` прошли живой прогон на откликах, включая удаление
    навыков под лимит и восстановление резюме. При сбое модели отклик уходит
    на текущем резюме.

## `tailoring.skills`

| Поле | Тип | Обяз. | По умолчанию | Описание |
|---|---|---|---|---|
| `enabled` | bool | нет | `false` | Включить подбор навыков. |
| `maximum` | number | **да** при `enabled` | — | Верхняя граница навыков в резюме (платформенный лимит). |
| `allow_removals` | bool | нет | `false` | Разрешить модели помечать `remove`. Удаления применяются только в объёме, нужном чтобы добавленные теги вместились в `maximum`; лишние игнорируются, удалить несуществующие или все навыки нельзя. |
| `model` | object | нет | — | Model policy выбора навыков (`provider`, `prompt_version`, `instruction`, `timeout`). Без модели работает детерминированная политика `add_vacancy_skills`. |

Политика без модели добавляет все допустимые `key_skills` вакансии, сохраняя
порядок существующих навыков; если лимит превышен, план отклоняется и
tailoring пропускается (отклик уходит на текущем резюме). При временной ошибке
модели навыки остаются как есть; детерминированный fallback не удаляет ничего.

## `tailoring.about`

| Поле | Тип | Обяз. | По умолчанию | Описание |
|---|---|---|---|---|
| `enabled` | bool | нет | `false` | Включить переписывание «О себе». |
| `maximum_runes` | number | **да** при `enabled` | — | Предел длины результата. |
| `model` | object | **да** при `enabled` | — | Model policy переписывания (`provider`, `prompt_version`, `instruction`, `timeout`). |

Контекст модели: текущий текст «О себе», наблюдаемое резюме (заголовок,
навыки, опыт, образование, языки), контекст вакансии. Локальный validator
отклоняет пустой и слишком длинный текст, служебные JSON/code-fence ответы,
незаявленные плейсхолдеры и неподтверждённые числа/URL/e-mail. Любая ошибка
модели или валидации оставляет текущий текст и не блокирует отклик; при
`contacts` профиля модель сохраняет контакты в самом верху.

## `experience`

Модель переписывает описания мест работы под вакансию. Резюме может содержать
много блоков, поэтому write/readonly задаются объектами, а блоки перечисляются
явно:

```json
"experience": {
  "enabled": true,
  "groups": [
    {
      "write": ["experience.2644170581.description"],
      "readonly": ["title", "keySkills", "experience.2644170582"],
      "maximum_runes": 900,
      "model": {"provider": "deepseek", "prompt_version": "v1", "instruction": "Сожми описание и сделай акцент на Go и Kafka.", "timeout": "60s"}
    },
    {
      "write": ["experience.2644170582.description", "experience.order"],
      "model": {"provider": "deepseek", "prompt_version": "v1", "instruction": "Перефразируй под вакансию и поставь самый релевантный блок первым.", "timeout": "60s"}
    }
  ]
}
```

- **Группы** — несколько независимых запросов внутри одного шага tailoring:
  у каждой группы свои блоки, инструкция, `readonly`-контекст и лимит длины;
  один блок нельзя писа́ть из двух групп. Без `groups` работает одиночная
  форма (`write`, `readonly`, `maximum_runes`, `model`).
- **Объекты**: `title`, `about`, `keySkills`, `experience.<id>`,
  `experience.#N` (по позиции, если платформа скрывает id),
  `experience.<id>.description`, `experience.order`.
- **`experience.order`** разрешает модели вернуть новый порядок блоков;
  принимается только полная перестановка всех блоков.
- Ответ проверяется детерминированно: id должны существовать, описания не
  длиннее лимита, числа, e-mail и ссылки обязаны быть в исходном описании или
  вакансии. Ошибка группы пропускается, остальные группы продолжают; при
  полном провале резюме остаётся текущим.

## Chain и восстановление

Если включены и `skills`, и `about`, процессоры объединяются в chain:
совпадающие пути отклоняются на этапе плана. Разрешённые пути определяются
резюме профиля — пользователь не задаёт JSON Pointer вручную.

При внешнем изменении резюме во время саги состояние не перезаписывается:
saga переходит в `recovery_required` и блокирует следующий tailoring профиля
до ручного разбора. Активная фаза и redacted diff видны в dashboard.
