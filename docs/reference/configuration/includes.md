# `include` и сборка конфига

`include` собирает один runtime-конфиг из нескольких файлов. Итог существует
только в памяти; сгенерированный общий файл не создаётся.

## Пример

```json
"include": [
  "adapters/*.json",
  "profiles/primary.json",
  "searches/golang.json"
]
```

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| элемент массива | string | **да** | Путь или glob-маска относительно файла, объявившего `include`. |

## Порядок и правила

1. Файл подключается depth-first после собственных объектов основного файла.
2. `database` и `server` разрешены только в главном файле — фрагменты не
   переопределяют инфраструктуру.
3. Повтор `tag` между файлами отклоняется, как и опечатка в ссылке.
4. Циклы include и глубина больше 16 запрещены.
5. Glob без совпадений — ошибка (не молчаливый пропуск).
6. Относительные ссылки на файлы внутри фрагмента (`resume_facts_file`,
   `message_template_file`, `bootstrap.source`, `answer_sets`) разрешаются
   относительно **объявившего** их файла, поэтому фрагменты переносимы.

## Секреты и окружение

- ключи моделей — только через `api_key_env`;
- OAuth-креденшелы — через `credentials_ref`, browser state — в `state_file`;
- сам конфиг не должен содержать токенов и cookies и может лежать в Git,
  если в нём нет персональных данных (`contacts`, `resume_facts_file` с
  фактами — держите локально).

## Проверка

`job-agent -migrate-up <config>` и запуск сервиса валидируют собранный конфиг и
указывают файл и поле с ошибкой. Быстрая проверка конфига без запуска:

```bash
job-agent-check <config>   # ready | degraded | blocked
```

Разбор частых ошибок — в [Runbook](../../runbook.md).
