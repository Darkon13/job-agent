# Очистка откликов

## Что удаляется

GC убирает локальный объект `Application` из SQLite и dashboard. Это **не**
удаление отклика на HH и **не** очистка переписки. Сообщения, чаты, вакансии,
состояние квоты и интервалы отправки сохраняются. Завершённые snapshots
подстройки резюме, принадлежащие удаляемому отклику, удаляются вместе с ним;
незавершённая подстройка блокирует очистку.

Вместо полного объекта остаётся минимальная tombstone: ключ профиль/вакансия,
ID, причина, время удаления и итоговый статус. Она предотвращает повторный
отклик при следующем поиске. Итоги завершённых рассылок читают живые объекты
либо tombstones, поэтому очистка не переписывает историю успехов. Служебные
budget/pacing записи не удаляются: GC не освобождает уже потраченный лимит.
Тексты писем и snapshots в tombstone не копируются.

## Автоочистка

Отдельный job `application.retention` получает актуальные платформенные
статусы, обновляет локальное представление и создаёт `application.remove`:

- подтверждённый отказ — подходит при `remove_rejected: true`;
- отправленный отклик в ожидании приглашения — подходит, когда с отправки
  прошло `stale_after`, даже если работодатель смотрел отклик или писал в чат;
- приглашение, неизвестный/скрытый статус, отсутствующая или неоднозначная
  связь с откликом — не удаляются автоматически.

Удаление теперь не только локальное: перед снятием записи worker отзывает
отклик на платформе — ожидающий отменяется (`decline`), закрытый или скрытый
уходит в архив (`trash`) вместе с чатом переговоров. Локальный tombstone
сохраняет историю и dedup. Для профилей без платформенного наблюдателя
(например, импортированная история) семантика остаётся локальной. Свежее
состояние из retention переиспользуется в течение 10 минут, поэтому серия
удалений не перечитывает весь список откликов на каждую запись.

Если отклик ещё связан с running-кампанией или незавершённой tailoring saga,
локальное удаление отклоняется временной ошибкой и задача повторяется после
завершения владельца; permanent failure для этого случая не создаётся.

Пример объекта в массиве `jobs` (в примере выключен):

```json
{
  "tag": "cleanup-primary-applications",
  "enabled": false,
  "triggers": [{
    "type": "cron",
    "expression": "0 3 * * *",
    "timezone": "Europe/Moscow",
    "misfire": "run_once"
  }],
  "concurrency": "forbid",
  "action": {
    "type": "application.retention",
    "profile": "primary",
    "retention": {
      "stale_after": "336h",
      "remove_rejected": true
    }
  }
}
```

`336h` — 14 дней; `720h` — 30 дней. Срок обязателен и должен быть положительным;
14 дней не зашиты в worker. Формат — Go duration (`h`, `m`, `s`), не `14d`.
`remove_rejected` по умолчанию `true`; отключение этой опции не отключает
очистку старых ожидающих откликов.

Перед выполнением каждой GC-задачи worker повторно читает статусы платформы.
Приглашение, пришедшее после формирования очереди, останавливает удаление.
Наблюдение старше пяти минут, время из будущего, неполная пагинация и дубли
negotiation ID отклоняются. По возможности связь определяется точным
negotiation ID; иначе совпадение по вакансии допустимо только при единственном
варианте. Два резюме на одну вакансию не разрешают выбирать произвольный отклик.

Repository повторяет проверку состояния и timestamp под write lock/в одной
транзакции. Новое локальное наблюдение между чтением worker и записью GC
не позволяет удалить объект по старой проверке. Платформа и SQLite не образуют
общую транзакцию: гарантия относится к последнему полученному наблюдению.

Сейчас HH observer читает `/negotiations` через OAuth/API. Для профиля,
авторизованного только browser cookies, автоматическая синхронизация статусов
и GC пока **не реализованы**. Включённый job без observer даёт явную ошибку
старта, а не исчезает из расписания. Это не мешает ручной локальной очистке.
Существующие чаты не служат доказательством invitation/discard.

## Поиск, выбор и действие

`GET /api/v1/applications` — отдельный список объектов, вне dashboard summary.
Поддерживает `q`, `employer`, `profile_id`, `status`, `group`, `sort`, `offset`,
`limit` (1–200). Ответ содержит `items`, `total`, `groups`, `offset`, `limit`.

Пример: `/api/v1/applications?employer=Sber&sort=updated_asc&limit=200`.
`q` ищет по вакансии, компании, профилю и decision code. Регистр, включая
кириллицу, не важен. Сортировки: `updated_desc`, `updated_asc`, `employer_asc`,
`title_asc`. `group` поддерживает категории dashboard; `sent` объединяет
отправленные отклики независимо от текущего ответа работодателя.

Поиск и подсчёт категорий выполняются до пагинации по всей локальной базе,
а не по первым 200 объектам. Текущая реализация сканирует лёгкую проекцию
метаданных и сортирует в Go для одинакового Unicode-поведения SQLite/memory.
Это O(N) памяти, O(N log N) сортировки; full-text/indexed query — отдельная
оптимизация для больших историй. Письма и snapshots в эту проекцию не входят.

Dashboard позволяет выбрать видимые объекты (до 200 за действие). При смене
страницы или фильтра выбор сбрасывается, чтобы не удалять скрытые от пользователя
элементы. Запрос:

```http
POST /api/v1/applications/remove
Idempotency-Key: selection-unique-key
Content-Type: application/json

{"application_ids":["application-a","application-b"]}
```

Ответ `202` означает постановку задач, **не** завершение удаления. `results`
содержит результат по каждому ID: `task_id` либо `error: not_enqueued`.
Частично подходящая выборка не скрывает уже созданные задачи за общей ошибкой.
Активные отклики, работающая рассылка и незавершённая resume saga защищены от
очистки. Ошибки выполнения видны в списке failed tasks. Для приглашений ручное
выделение является явным разрешением; дополнительного approve нет.

Повтор ручной команды возвращает ту же durable task даже после удаления строки.
Retry worker после DB commit не требует повторной внешней операции. GC-задачи
разделены по запуску: старый пропущенный GC не блокирует последующий ручной выбор
или новую проверку на следующем запуске.

## Проверки и эксплуатация

Миграции 19–20 добавляют tombstones и platform states, отделяют срок жизни
accounting/campaign ссылок от полного `Application`. Делать backup нужно до
первого GC. После фактического удаления downgrade ниже схемы 19 намеренно
отклоняется: откат схемы не способен восстановить удалённые письма/snapshots.
Восстановление выполняется из backup; принудительный сброс dirty version не
является восстановлением данных.

Проверки: `go test -race ./...`, `go vet ./...`. Контрактные тесты выполняют
GC на SQLite и memory, проверяют квоты, pacing, чаты, историю рассылки,
идемпотентность, новый invitation и поиск старых объектов за первой страницей.
Браузерный smoke в `cmd/job-agent-dashboard/testdata/gc-browser-smoke.js`
полностью подменяет API и локальные assets, не обращаясь к HH.

Ближайшее продолжение: browser-cookie observer статусов HH, отдельная
синхронизация без GC, точный live flow конкретного job по correlation ID.
