# Горячая перезагрузка конфига

## Проблема

Любая правка `config.json` сейчас требует перезапуска сервиса. Для расписаний,
поисков и политик это лишние простои: scheduler уже умеет `Sync`, но вызывается
только на старте.

## Целевая схема

1. **Триггер**: сигнал `SIGHUP` (первая фаза) и файловый watcher с debounce
   (вторая фаза). Изменение фиксируется по mtime+digest, не по размеру.
2. **Проверка**: новый конфиг полностью загружается и валидируется в памяти;
   при ошибке логируется причина, старый конфиг продолжает работать.
3. **Атомарная замена горячей части**:
   - расписания и job-дефиниции — `scheduler.Sync` с новым набором;
   - поиски, маршруты и цели кампаний — для новых запусков; запущенные кампании
     доигрывают по снимку, с которым стартовали;
   - `answer_sets`, `employer_groups`, пулы писем, tailoring-политики — для
     новых задач;
   - модели — пересоздание клиентов при смене провайдера/модели;
   - профильные `applications`-политики — для новых задач профиля.
4. **Статус в dashboard**: версия конфига (digest), время последней удачной
   перезагрузки, последняя ошибка — чтобы видеть состояние без логов.

## Что требует рестарта

- `database.path` (файл БД уже открыт);
- `server.listen` / `exposure` / `api_token_env`;
- настройки адаптеров (например, адрес browser-worker);
- `state_file` профиля — применяется на рестарте, чтобы не рвать живую сессию.

## Инварианты

- In-flight задачи не отменяются и не переписываются: они завершаются по старому
  снимку; всё новое берётся из нового конфига.
- Секреты из конфига не логируются; ошибка показывает путь к файлу и JSON-поле.
- Перезагрузка идемпотентна: повторный сигнал без изменений ничего не делает.

## Фазы

1. `SIGHUP` + полная валидация и применение горячей части, статус в логах.
2. Watcher (`fsnotify`) с debounce 1–2 секунды и защитой от частичной записи.
3. Конструктор в dashboard: правки через API пишутся в конфиг и запускают ту же
   перезагрузку, с diff и подтверждением.
